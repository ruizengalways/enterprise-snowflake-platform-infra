# Terraform Standards

## Scope

These standards apply to `enterprise-snowflake-platform-infra`.

## Version policy

- Terraform CLI is pinned by `.terraform-version`.
- Snowflake provider is pinned exactly in each root stack.
- Current baseline: Terraform `1.16.0`, `snowflakedb/snowflake` provider `2.19.0`.
- Provider upgrades are deliberate changes with migration-guide review and CI validation; do not use an unbounded `latest` constraint.
- `.terraform.lock.hcl` is committed once generated by `terraform init` in a connected development/CI environment.

## Authentication

Never place credentials, private keys, OAuth tokens, PATs, or account secrets in Git.

Provider configuration reads authentication material from supported Snowflake provider environment/config mechanisms. Root stacks may set role aliases but do not hard-code credentials.

Initial administrative aliases:

- `snowflake.sysadmin` — database, schema and warehouse lifecycle.
- `snowflake.securityadmin` — account-role hierarchy and grants.

Workload Identity Federation / GitHub OIDC is the target CI/CD authentication mechanism. It is intentionally not configured until the service-user/role trust model is implemented and tested.

Do not use `ACCOUNTADMIN` as a normal Terraform execution role. Resources that genuinely require `ACCOUNTADMIN` must be isolated and justified.

## State

The repository does not commit Terraform state.

A durable remote backend is required before automated apply to shared NONPROD or PROD. Backend technology is intentionally not guessed in the bootstrap commit because no cloud/state platform has been selected yet.

Until a remote backend ADR is accepted:

- CI may run `fmt`, `init -backend=false`, and `validate`.
- local exploratory plans are allowed only with non-secret local inputs and must not be treated as authoritative shared state.
- automated apply is disabled.

## Root stack pattern

Deployable roots live under:

```text
terraform/stacks/nonprod/
terraform/stacks/prod/
```

Each root stack:

1. pins Terraform/provider versions;
2. configures provider aliases;
3. reads its environment YAML from `config/environments/`;
4. composes reusable modules;
5. contains no credentials;
6. exposes useful object-name outputs;
7. does not contain project business logic.

## Module pattern

Modules live under `terraform/modules/` and own one cohesive platform capability.

Initial modules:

- `analytics-environment` — analytics database plus stable schemas.
- `warehouse` — standard warehouse guardrails.
- `platform-control` — `PLATFORM_CONTROL` database and structural schemas.
- `rbac` — account roles, database roles and role hierarchy.

Do not create a module only to wrap a single line or to hide business-specific differences.

## Resource ownership

Terraform owns stable platform infrastructure and RBAC objects selected in the object-ownership matrix. It does not own dbt models, project business transformations, or routine data changes.

One Snowflake object has one authoritative owner. Do not also create a Terraform-owned object through dbt or ad-hoc migration SQL.

## Naming and metadata

Object names come from environment/project configuration and must follow `NAMING_CONVENTIONS.md`.

Configuration may describe stable technical facts such as database names, schema sets, retention, warehouse size and timeout guardrails. Credentials are never configuration metadata.

## Warehouse defaults

Baseline warehouses use conservative settings unless a workload demonstrates a different need:

- standard warehouse type;
- `XSMALL` initial size;
- auto-resume enabled;
- auto-suspend enabled, normally 60 seconds;
- initially suspended;
- explicit statement timeout;
- no query acceleration by default;
- no multi-cluster scaling without evidence.

Cost/resource monitors are a later Phase 1 capability because provider management may require a stronger administrative role and should not silently force routine Terraform to use `ACCOUNTADMIN`.

## Validation

Every Terraform change must pass:

```text
terraform fmt -check -recursive
terraform init -backend=false
terraform validate
```

for each root stack.

Plan/apply checks are added only after account authentication and remote state are established.
